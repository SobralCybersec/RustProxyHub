01 · The Problem
Why a hub

Every provider speaks a different dialect

Seven AI backends means seven SDKs, seven auth schemes, seven streaming quirks. Wiring them into one app is where projects drown.

The friction
  • API fragmentation :different request shapes, error formats, and token limits per vendor.
  • Auth sprawl :API keys, OAuth, and browser-only sessions all at once.
  • Streaming differences :every provider frames SSE and cutoffs its own way.
  • Deployment weight :separate runtimes, Node processes, and browsers to ship.
without a hub
import OpenAI from "openai";
import { GoogleGenAI } from "@google/genai";
import Anthropic from "@anthropic-ai/sdk";
// …plus Qwen, Mistral, DeepSeek, Kimi

// four SDKs, four auth flows, four
// streaming formats, in one client.
if (model.startsWith("gpt"))      useOpenAI();
else if (model.startsWith("gem")) useGemini();
else if (model.startsWith("qwen"))useQwenBrowser();
// …and it grows with every provider

RustProxyHub collapses all of it behind one OpenAI-compatible endpoint.

What it is

A local, OpenAI-compatible proxy hub

Point any OpenAI-style client at localhost:3100. RustProxyHub routes each request to the right provider, streams the reply back, and shows live health in a desktop dashboard.

unified api

One endpoint

/v1/chat/completions, /v1/models and /v1/messages: the interface every tool already knows.

7 providers

Prefix routing

qwen: · chatgpt: · gemini: · mistral: · deepseek: · kimi: · zai: pick the backend by model name.

streaming

SSE passthrough

Token-by-token text/event-stream responses relayed straight from the upstream provider.

browser-backed

Session providers

Playwright drives login-only providers like Zai, no public API key required.

desktop

Single bundle

Tauri packages the Rust server, Node bridge and WebView2 UI into one installer.

observability

Live dashboard

Vue 3 + Pinia dashboard pushes provider health and logs in real time, no polling.

05 · Routing
Pick a backend

Routing by model prefix

The part before the colon selects the provider; everything after is the real model id. Unknown prefixes fall back to inference.

runtime/hub_impl/main.rs · L796
fn normalize_prefixed_model(model: &str) -> RoutedModel {
    let trimmed = model.trim();
    if let Some((prefix, actual)) = trimmed.split_once(':') {
        let provider = match prefix.to_ascii_lowercase().as_str() {
            "deepseek" => ProviderName::Deepseek,
            "kimi"     => ProviderName::Kimi,
            "qwen"     => ProviderName::Qwen,
            "chatgpt"  => ProviderName::Chatgpt,
            "gemini"   => ProviderName::Gemini,
            "mistral"  => ProviderName::Mistral,
            "zai"      => ProviderName::Zai,
            _ => infer_provider(trimmed),
        };
        // → RoutedModel { provider, model: actual }
    }
}

07 · Health
Is everyone up?

Health checks, all at once

Every provider is pinged concurrently with join_all; the results feed both /health and the live dashboard. One slow backend never blocks the rest.

runtime/hub_impl/main.rs · L498
async fn provider_health_checks(state: &AppState)
    -> Vec<ProviderHealth> {
  join_all(PROVIDER_ORDER.into_iter().map(|provider| async move {
    let config = state.provider_config(provider);
    let res = provider_request(&state.client, config,
                               Method::GET, "/health").send().await;
    match res {
      Ok(r) => ProviderHealth {
        provider, healthy: r.status().is_success(),
        status_code: Some(r.status().as_u16()),
        detail: r.json::<Value>().await.ok(),
      },
      Err(_) => ProviderHealth { provider, healthy: false, .. },
    }
  })).await
}
Why it matters
  • Concurrent :join_all fans out all 7 pings in parallel.
  • Fault-tolerant :an unreachable provider becomes healthy: false, not a crash.
  • Structured :status code + JSON detail captured per provider.
  • Ordered :PROVIDER_ORDER keeps the UI stable frame to frame.

08 · Streaming
Token by token

SSE, framed by hand

Responses are streamed as text/event-stream. Each chunk is a data: line; the stream ends with [DONE], exactly what OpenAI clients expect.

runtime/providers/qwen_impl/main.rs · L1907
fn sse_json(value: Value) -> Bytes {
    Bytes::from(format!("data: {}\n\n", value))
}
fn sse_done() -> Bytes {
    Bytes::from("data: [DONE]\n\n")
}

fn stream_response<S>(stream: S) -> Response
where S: Stream<Item = Result<Bytes, Infallible>> + Send + 'static {
    Response::builder()
        .status(StatusCode::OK)
        .header(CONTENT_TYPE, "text/event-stream")
        .header(CACHE_CONTROL, "no-cache, no-transform")
        .header(CONNECTION, "keep-alive")
        .header("x-accel-buffering", "no")
        .body(Body::from_stream(stream))
        .expect("valid streaming response")
}
On the wire
response stream

  • x-accel-buffering: no :defeats proxy buffering for instant tokens.
  • keep-alive :one connection for the whole generation.
  • Body::from_stream :backpressure-aware relay from upstream.

#[tauri::command]
async fn start_service(
    state: State<'_, ControlState>, name: String,
) -> Result<(), String> {
    let name = normalize_service_name(&name)
        .map_err(|e| e.to_string())?;
    if state.service_status(name).await.running {
        return Err(format!("{} already running", name));
    }
    state.ensure_service_dir(name);
    state.spawn_service_by_name(name)
        .map_err(|e| e.to_string())
}
